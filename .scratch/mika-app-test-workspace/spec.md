# Mika 移动端 App 自动化测试工作区规格

Status: ready-for-agent

## Problem Statement

测试人员需要在 Android 手机上验证同一台手机中的目标 App。现有 Mika 能操作手机应用，但每次探索都可能重复调用模型，消耗较多 token；运行轨迹虽然包含步骤结果和截图，却尚未成为可交付的测试报告；成功操作、测试用例和可分享技能之间也缺少清晰的复用路径。用户还需要在保留 Mika 全部功能的独立测试 App 中管理用例，并能在 App 内获取经过验证的 Mika 上游更新。

## Solution

交付独立安装和更新的 Android App“MP工作台”，保留 Mika 的完整功能并增加本机测试工作区。测试人员可创建、编辑和管理版本化测试用例，输入自然语言或导入 YAML/JSON 契约，在同一台手机上运行目标 App。运行优先使用符合安全条件且与当前界面匹配的 Mika 路线回放；路线不匹配或无法应用时交还现有 LLM 操作流程。所有运行仍根据当前界面验证结果，路线回放不能取代断言或业务证据核验。

MP工作台从现有 `TaskService` 执行任务，并复用 `RunStore` 中的事件和截图。测试报告以现有运行时间线为基础，呈现步骤、状态、耗时、可用的模型 token 统计、截图和断言证据，支持 HTML、ZIP 与 PDF。成功运行后，用户可以确认将任务保存为版本化用例，并选择生成或关联一份操作技能；技能是可分享的辅助知识，用例契约才是执行和判定的规范记录。分享包以用例为中心，包含兼容的安全路线与可选技能，并在导出前剔除秘密。

MP工作台提供自己的手动检查和下载更新入口。上游 Mika 源码先同步到 MP工作台代码，再通过构建和回归后发布到独立更新通道。下载和校验期间用户可继续使用 App；有测试运行时延后安装；空闲后调用 Android 安装流程更新完整 APK，安装时 App 会短暂重启。任务、报告和本机数据在升级后保留。运行中热替换 Mika 内核不属于本规格。

## User Stories

1. As a 移动端测试人员, I want 在 MP工作台中访问完整的 Mika 功能和测试工作区, so that 我能在保留日常 Mika 使用方式的同时管理测试。
2. As a 移动端测试人员, I want 在手机本地创建项目和测试套件, so that 测试用例能按产品和测试范围组织。
3. As a 移动端测试人员, I want 创建、编辑、复制、移动、归档、恢复和删除测试用例, so that 我能维护完整的本机用例库。
4. As a 移动端测试人员, I want 搜索用例名称、命令和标签, so that 我能快速定位要运行的测试。
5. As a 移动端测试人员, I want 用自然语言命令创建测试用例, so that 我能从探索性测试开始而不必先写结构化步骤。
6. As a 移动端测试人员, I want 导入并导出 YAML 或 JSON 任务契约, so that 既有步骤文件可以进入工作区，且用例可以离线传递。
7. As a 移动端测试人员, I want 在导入冲突时选择创建新修订、另存副本或跳过, so that 既有用例不会被意外覆盖。
8. As a 移动端测试人员, I want 查看每个用例的修订历史并运行指定修订, so that 历史测试结果可以对应到精确的测试定义。
9. As a 移动端测试人员, I want 每次运行保存其契约修订快照, so that 后续修改或删除用例不会改变已完成运行的含义。
10. As a 移动端测试人员, I want 从手机端选择同机已安装的目标 App 并启动测试, so that 执行不依赖远程设备或目标 App 专用测试 SDK。
11. As a 移动端测试人员, I want 可重复的安全界面操作优先尝试 Mika 路线回放, so that 稳定流程能减少重复模型调用和 token 消耗。
12. As a 移动端测试人员, I want 路线不匹配或执行不完整时自动交还 LLM, so that 页面变化不会让自动化盲目继续或直接中止。
13. As a 移动端测试人员, I want 路线回放后仍由 Mika 检查当前界面并核验结果, so that 节省模型调用不会降低测试结论可信度。
14. As a 移动端测试人员, I want 看到路线回放、模型调用、重试和 token 用量的区别, so that 我能了解一次运行的成本及其来源。
15. As a 移动端测试人员, I want 每次运行有唯一运行 ID 并记录有序动作、观察、结果和截图, so that 报告、用例、路线和沙箱数据可以相互追溯。
16. As a 移动端测试人员, I want 从成功运行中确认创建或更新一条版本化测试用例, so that 有效的探索结果可以成为可复跑资产。
17. As a 移动端测试人员, I want 失败运行保留为报告并能从中复制用例以修订, so that 失败轨迹可以用于诊断而不会自动变成不可靠的复用流程。
18. As a 移动端测试人员, I want 在成功运行后可选择生成或关联一份 Mika 技能, so that 操作知识可以辅助其他任务而不会替代正式测试契约。
19. As a 测试人员, I want 将用例契约、兼容的安全回放路线和可选技能打包分享, so that 另一台 MP工作台可以导入并复用测试资产。
20. As a 测试人员, I want 分享包标记目标 App 与兼容信息, so that 接收端能判断是否可以使用其中的回放路线。
21. As a 测试人员, I want 不兼容或不安全的路线被跳过并回退到 LLM 执行, so that 分享资产不会绕过运行时验证。
22. As a 测试人员, I want 在运行结束后看到以运行过程时间线为主体的报告, so that Mika 已记录的步骤和结果可以直接用于复盘。
23. As a 测试人员, I want 报告呈现每步状态、动作、前后台焦点变化、耗时、重试和可用的模型 token 统计, so that 我能分析失败原因和 token 消耗。
24. As a 测试人员, I want 报告中的错误和失败断言关联当时截图及相邻事件, so that 我能定位问题发生的界面与动作。
25. As a 测试人员, I want HTML 报告展示结论、断言、轨迹与关键截图, so that 我可以在手机上检查一次运行。
26. As a 测试人员, I want ZIP 包含完整允许导出的报告、事件和运行截图, so that 我能离线存档或交付证据。
27. As a 测试人员, I want 从报告导出 PDF 并在正文保留失败步骤和关键检查点截图, so that 报告可供审阅且文件大小可控。
28. As a 测试人员, I want 报告和导出包关联运行 ID、用例版本、模型策略和软件版本, so that 不同运行结果可比较和追溯。
29. As a 测试人员, I want 报告展示实际可得的 token 计数并区分服务端未报告的用量, so that 未知数据不会被误认为精确成本。
30. As a 测试人员, I want 报告证据在 Mika 运行记录轮转清理后仍遵循工作区保存策略, so that 已归档的重要报告不会因底层轨迹清理而无提示丢失。
31. As a 测试人员, I want 硬断言必须由约定的业务证据通过且不能被 LLM 推翻, so that 订单和支付等关键事实不会被语义解释覆盖。
32. As a 测试人员, I want LLM 仅解释软性语义断言并提供证据摘要, so that 模糊页面结果仍可被评估并审阅。
33. As a 测试人员, I want 提交交易后的结果不确定时只执行只读核查, so that 系统不会盲目重复下单或支付。
34. As a 测试人员, I want 在隔离的支付沙箱中验证完整交易流程, so that 可以覆盖结账和支付后的业务状态而不触及真实资金。
35. As a 测试人员, I want 沙箱凭证仅在本机任务执行中使用且分享或报告导出时被剔除, so that 可复用资产不会泄露秘密。
36. As a 测试人员, I want 沙箱记录携带运行 ID 并遵循任务清理策略, so that 测试数据可核对且可审计。
37. As a 测试人员, I want 自动化期间的用户触屏和焦点变化进入时间线, so that 即使运行继续并通过，报告仍能解释人工介入。
38. As a 测试人员, I want 在 Android 12 及以上设备上看到前台焦点限制和执行状态, so that 我能理解自动操作与日常使用之间的影响。
39. As a MP工作台用户, I want 在 App 内手动检查并下载独立更新, so that 我可以在手机上获取经过验证的 MP工作台版本。
40. As a MP工作台用户, I want 在更新下载和校验期间继续使用当前 App, so that 获取升级不会阻塞当前工作。
41. As a MP工作台用户, I want 活跃测试运行期间延后安装, so that 更新安装不会中断正在执行的测试。
42. As a MP工作台用户, I want 空闲后通过 Android 安装流程更新完整 MP工作台 APK, so that 安装过程和权限由系统处理。
43. As a MP工作台用户, I want APK 安装重启后保留用例、运行报告、技能和设置, so that 独立升级不影响本机测试资产。
44. As a MP工作台维护者, I want 将 Mika 上游代码同步到 MP工作台后先构建和回归再发布, so that 用户只会下载经过验证的独立测试 App 更新。
45. As a MP工作台维护者, I want 运行报告标记 MP工作台版本和 Mika 上游提交标识, so that 报告能对应到具体软件构建。
46. As a Mika 用户, I want 原 Mika 应用保留官方功能和官方更新通道, so that MP工作台更新不会替换或冒充官方 Mika。

## Implementation Decisions

- MP工作台是独立 application ID、签名配置和更新通道的完整 Android App，保留 Mika 原有用户功能；官方 Mika 应用与其官方更新通道不变。
- 测试用例采用本机项目 → 测试套件 → 用例层级。用例主体是带 schema 版本的任务契约，包含命令、步骤、目标 App、断言、固定模型策略版本及沙箱/清理配置。修订追加保存，单次运行固定引用一个契约快照。
- 测试工作区支持 JSON/YAML 导入导出、搜索、标签、创建、编辑、复制、归档、恢复和删除。导入 ID 冲突必须明确选择覆盖为新修订、另存副本或跳过。已有测试任务文件迁移到默认项目和套件。
- `TestExecutionService` 是测试工作区到现有执行流程的入口，调用 `TaskService`，不复制 Mika 的手机操作或模型编排实现。运行事件和截图使用现有 `RunStore`。
- Mika 现有安全路线记录与回放作为节省 token 的首选路径。只有路线匹配且完整时才重用其动作；路线不匹配、执行异常或无法安全记录时交还 LLM。所有路线回放结果仍需当前运行的结果核验和断言判定；不得用路线成功计数替代业务证据。
- 复用现有路线记录器的安全限制。需要用户接管/确认、支付、受保护界面、密码/秘密输入、浏览器或沙箱专用工具、步骤不完整等运行不生成可回放路线。不得为了提高回放覆盖率放宽这些限制。
- 测试工作区不把每次原始运行自动转换成技能。成功运行后由用户确认是否提升为版本化用例；技能可选生成或关联，并作为可分享的辅助操作知识。失败运行保留为报告，可由用户复制并修改为新用例。
- 分享资产以版本化测试用例契约为主，可附带经安全筛选的 Mika 路线与用户选择的技能。导入时校验契约版本、目标 App 和路线兼容性；不兼容路线不回放，任务仍可走 LLM 路径。分享和报告导出统一剔除沙箱凭证及已标记秘密。
- `TestRunRepository` 是报告与用例运行证据的读取/投影边界：以 `RunStore` 事件、截图、运行时长、重试和服务端报告的 token 数生成报告数据，并关联运行 ID、契约快照、断言和版本元数据。它不另建一套动作采集系统。
- 报告时间线沿用 Mika 现有运行过程视图的信息架构。HTML 显示结论、断言和关键步骤证据；ZIP 保留允许导出的完整事件与截图；PDF 展示失败项和关键检查点截图。失败或错误步骤必须有截图或明确的截图缺失原因。
- Token 报告按实际 `RunStore` 模型回复事件累计 input、cached input 和 output 计数，并区分未报告用量；路线回放步骤与 LLM 调用分别统计。不将截图本身当作节省 token 的机制，也不伪造精确费用。
- 报告和用例快照按工作区保存策略管理，并须处理底层 `RunStore` 的有界保留：重要归档证据不能在不告知用户的情况下随着普通运行轮转丢失。
- 测试继续使用固定版本模型策略、硬/软断言分离和不确定交易结果只读核查。总体 PASS 要求所有必需硬断言通过，并满足必需软断言策略；LLM 无权覆盖交易硬证据失败。
- 用户触屏、前后台切换和焦点变化记录在运行轨迹中。用户可以继续使用手机，人工交互本身不使运行自动失败；结论仍按断言产生并保留人工交互证据。
- 更新沿用现有 `UpdateChecker` 与 `ApkUpdater` 的更新检查、下载、完整 APK 校验和 Android 安装流程，增加 MP工作台专属更新源与活跃测试运行状态协调。下载期间 App 可用；有测试运行时不启动安装；空闲后由用户通过系统安装流程应用更新。完整 APK 安装会重启 App，更新后保留本机数据。
- MP工作台独立发布流程同步 Mika 上游源码，完成构建和回归后发布 MP工作台自己的 APK。报告保留 MP工作台版本及 Mika 上游版本/提交信息。该流程不直接安装原 Mika APK，也不改变原 Mika 更新通道。

## Testing Decisions

- 测试以外部可见行为为准：给定契约和屏幕状态，验证是否选中安全路线、路线偏离后是否交还 LLM、断言是否保持正确、轨迹和截图是否对应、报告/分享包是否完整且秘密已剔除、APK 更新是否只在安全时机安装。避免只断言私有方法调用或实现细节。
- 主要运行接缝为 `TestExecutionService` → 现有 `TaskService` → `RunStore`；报告和分享数据通过 `TestRunRepository` 投影。此接缝已由用户确认。
- `:core` 测试覆盖路线记录安全限制、槽位脱敏、路线匹配/偏离、完整回放和回交 LLM；使用现有 `RouteRecorderTest`、`ReplayerTest` 和路线选择相关测试作为先例。
- `:app` 测试覆盖测试用例层级、修订快照、旧任务迁移、冲突导入、运行关联和报告投影；使用现有 `TestCaseRepositoryTest`、`TestExecutionServiceTest`、`RunStoreTest` 和 `RunTimelineViewModelTest` 作为先例。
- 报告测试验证步骤时间线、token 分类与未知计数、截图关联、报告持久化策略，以及 HTML/PDF/ZIP 输出；ZIP 内容需检查运行 ID、契约版本和截图，并确认沙箱凭证与秘密不会出现。
- 分享包测试验证 JSON/YAML 契约、可选技能和安全路线的打包/导入、版本兼容、不兼容路线跳过，以及目标 App 不匹配时仍能回退到 LLM。
- Android instrumentation 使用可控目标 App 与模型替身走现有 TaskService 路径，覆盖成功、失败、路线回放偏离、LLM fallback、截图、用户交互和不确定交易的只读核查。支付流程只连接隔离沙箱。
- 更新测试沿用 `UpdateCheckerTest`、APK 完整性测试及下载器测试先例，验证 MP工作台专属更新元数据、完整 APK 包名/签名/版本校验、下载期间状态、活跃运行延迟安装、空闲后系统安装交接及升级后数据保留。验证原 Mika 包名和官方更新源不会被改写。
- Android 12 及以上设备覆盖焦点限制场景；运行可继续时检查用户交互被记录且 PASS/FAIL 仍由断言决定。

## Out of Scope

- 云端测试用例同步、设备农场、远程手机控制和集中式远程调度。
- iOS 或 Android 12 以下支持。
- 运行中热替换 Mika 内核、应用内静默安装 APK，或绕过 Android 系统安装确认。
- 对目标 App 注入 SDK、修改其源码，或要求其提供专用测试接口。
- 真实资金、生产订单或未授权第三方系统上的交易；完整下单/支付流程仅限支付沙箱。
- 由 LLM 语义解释推翻订单、支付等硬断言失败。
- 保证 UI 变化时路线永远匹配或每次运行采取完全相同动作；路线仅在安全且匹配时复用，运行仍根据实时界面验证。
- 把技能作为具有硬断言、契约版本和运行证据的替代品，或自动把所有失败/未审阅运行发布成可分享技能。
- 将 MP工作台更新当作原 Mika 官方更新，或直接用原 Mika APK 覆盖 MP工作台。

## Further Notes

- 当前工作区已有版本化测试用例仓库和运行关联的初步实现；本规格明确后续路线复用、报告导出、分享包和更新运行协调需要补齐的产品行为。
- Mika 当前路线记录器已通过动作与事件筛选限制可记录范围；该安全边界是 token 优化方案的一部分，不是后续可随意放宽的实现细节。
- 当前 Mika 运行记录包含模型 token 统计字段，但有些服务端可能不报告用量。界面和导出必须区分实际计数、未报告和任何估算值。
- MP工作台升级更新的是完整应用包，安装时会短暂重启；用户可在下载期间继续使用 App，活跃测试完成前不应用更新。本机测试数据在安装更新后保留。
- 本地明文沙箱凭证风险仍存在；功能仅限测试沙箱，并必须在报告和分享包导出时执行秘密过滤。
