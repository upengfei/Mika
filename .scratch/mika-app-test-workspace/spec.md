# Mika 移动端 App 自动化测试工作区规格

Status: ready-for-agent

## Problem Statement

测试人员需要在 Android 手机上验证同一台手机中的目标 App。现有 Mika 能理解自然语言并操作手机 App，但它面向通用个人助理任务，缺少版本化测试任务、可重复调度、结构化断言、运行证据、失败截图和可交付报告。测试人员因此难以把一次成功的探索过程变成可追踪、可复跑、可审计的本机测试任务，也难以区分界面看起来成功与订单、支付等业务事实确实成功。

## Solution

交付一个独立安装和更新的 Android 测试 App。它完整保留 Mika 的现有用户功能，并增加测试工作区。用户可输入自然语言命令或导入 YAML/JSON 测试步骤，在手机本地创建版本化任务契约；每次手动或定时运行时，由契约锁定的 LLM 策略自主操作同机目标 App。测试工作区通过新增的 `TestExecutionService` 调用现有 `TaskService`，并复用 `RunStore` 保存运行事件和截图。

每次运行生成独立运行 ID 和轨迹，记录任务契约版本、Mika 上游版本、测试 App 版本、模型策略版本、目标 App、动作、观察、截图、用户触屏/焦点变化、断言及其证据。报告分开呈现硬断言和软性语义断言：LLM 可以解释软性结果，不能推翻订单、支付等硬证据失败。结果不确定时只允许只读核查，不自动重复提交、下单或支付。用户可导出 HTML 报告、含证据的 ZIP，并从报告导出 PDF。

测试任务、轨迹和调度均保存在手机本地。允许在任务中配置仅供支付沙箱使用的明文凭证，但 ZIP 导出必须剔除凭证。沙箱交易保留并关联运行 ID，按用户配置的清理策略处理。测试 App 有独立更新通道；Mika 上游仓库更新可同步到测试 App 代码，完成构建与回归验证后再发布测试 App 更新。原 Mika 的官方更新通道保持原样。

## User Stories

1. As a 移动端测试人员, I want 在 Mika 中打开测试工作区, so that 我可以在保留 Mika 全部现有能力的同时管理 App 自动化测试。
2. As a 移动端测试人员, I want 用自然语言描述测试目标, so that 我可以快速创建测试任务而无需先编写完整脚本。
3. As a 移动端测试人员, I want 导入 YAML 或 JSON 步骤文件, so that 已有的结构化测试流程可以进入手机端执行。
4. As a 移动端测试人员, I want 在运行前查看并保存解析后的版本化任务契约, so that 每次执行都能引用明确的目标、步骤、断言和策略版本。
5. As a 移动端测试人员, I want 选择本机已安装的目标 App, so that 自动化操作发生在同一台 Android 测试手机上。
6. As a 移动端测试人员, I want 使用当前 Mika 支持的手机操作能力执行目标 App, so that 测试不依赖目标 App 单独提供测试接口。
7. As a 移动端测试人员, I want 每次运行都由固定版本策略的 LLM 根据当前界面自主完成操作, so that 同一任务契约可按配置重新执行并审阅差异。
8. As a 移动端测试人员, I want 每次运行使用独立运行 ID 并记录完整动作与观察轨迹, so that 报告和沙箱数据可追溯到具体执行。
9. As a 移动端测试人员, I want 系统在执行期间记录用户触屏、前后台焦点和操作中断, so that 报告能解释设备交互对运行过程的影响。
10. As a 移动端测试人员, I want 自动操作在用户继续使用手机时仍可继续, so that 长时间测试不要求手机完全闲置。
11. As a 移动端测试人员, I want 用户在自动化期间操作手机后仍可依据断言得到 PASS 或 FAIL, so that 有人工交互的运行也能用于结果验证，同时保留该交互证据。
12. As a 移动端测试人员, I want 为每个任务定义硬断言和软性语义断言, so that 机器可核验的业务事实与需要语义解释的界面结果分别判定。
13. As a 移动端测试人员, I want LLM 对软性语义断言提供解释和证据摘要, so that 模糊的文案或页面状态可被合理评估。
14. As a 移动端测试人员, I want 订单、支付等硬断言必须由约定的业务证据满足, so that LLM 不能把实际交易失败解释为通过。
15. As a 移动端测试人员, I want 当交易提交后的结果不确定时只做只读核查, so that 系统不会因盲目重试而创建重复订单或重复支付。
16. As a 移动端测试人员, I want 配置本机定时调度和重复周期, so that 测试能在设备上按计划运行且不依赖远程调度服务。
17. As a 移动端测试人员, I want 完整运行测试支付环境的交易流程, so that 结账和支付后的界面及业务结果也能被验证。
18. As a 移动端测试人员, I want 在测试任务中配置仅用于支付沙箱的明文凭证, so that 沙箱登录流程能自动执行。
19. As a 移动端测试人员, I want 导出包自动剔除凭证和其他被标记的秘密, so that 可以分享测试证据而不泄露沙箱密钥。
20. As a 移动端测试人员, I want 沙箱订单保留运行 ID 并按策略清理, so that 测试数据可以核对、回收且不会失去运行关联。
21. As a 移动端测试人员, I want 失败的断言附带相关截图和事件上下文, so that 我可以快速定位失败发生在哪个页面和动作之后。
22. As a 移动端测试人员, I want 查看包含结论、断言、轨迹和证据的 HTML 报告, so that 我可以在手机上复盘一次测试。
23. As a 移动端测试人员, I want 导出包含报告与证据的 ZIP, so that 我可以离线归档或交付运行结果。
24. As a 移动端测试人员, I want 从 HTML 报告导出 PDF, so that 我可以提交可阅读的静态报告。
25. As a 移动端测试人员, I want 对比不同运行的结果并查看各自任务契约和策略版本, so that 我能区分产品回归与测试配置变化。
26. As a Mika 用户, I want 测试工作区之外的现有 Mika 操作、设置、存储和升级行为保持可用, so that 新增测试功能不取代通用助理体验。
27. As a 测试 App 维护者, I want Mika 上游代码同步后经过单独构建和回归再发布, so that 上游改进可进入测试 App，同时保留独立发布节奏。
28. As a 测试 App 维护者, I want 测试报告记录 Mika 上游版本与测试 App 版本, so that 运行证据对应到确切的软件构建。
29. As a Android 12+ 测试人员, I want 在 Android 12、13 的焦点限制下看到明确的设备状态和运行轨迹, so that 我可以理解自动化与前台使用之间的约束。

## Implementation Decisions

- 新增独立测试 App 分发产物，完整保留 Mika 用户功能并新增测试工作区。测试 App 使用独立 application ID、签名/发布配置和更新通道；官方 Mika 包名、用户功能及官方更新通道维持兼容。
- 测试工作区作为新增应用层能力接入现有 `TaskService`，不复制 Mika 的手机操作、模型调用和任务执行实现。新增 `TestExecutionService` 作为测试任务到通用任务执行的唯一高层接缝。
- 运行事件和屏幕截图使用现有 `RunStore` 持久化。测试功能增加关联元数据和测试报告投影；同一运行的任务契约版本、运行 ID、截图和 `RunEvent` 可相互追溯。
- 任务契约支持自然语言创建以及 YAML/JSON 导入，保存规范化后的版本化结构，至少表达目标 App、任务说明/步骤、断言、模型策略版本、沙箱配置引用和数据清理策略。导入格式需校验并给出可定位的错误；版本升级需保留既有任务可读性。
- 运行按保存的契约与固定模型/提示词策略执行，但每次仍由 LLM 根据当时观察自主决定动作。契约和策略版本固定以便复跑与审计，不承诺底层 UI 状态变化下每次动作完全确定。
- 断言分为硬断言和软性语义断言。硬断言要求可核验证据并拥有最终否决权；软断言可由 LLM 给出语义结论，但必须保留依据和解释。总体 PASS 要求所有必需硬断言通过，且所有必需软断言满足其策略。
- 交易安全策略覆盖提交状态不明确的情形：执行只读状态查询或订单核验，不再次执行具有副作用的提交/支付动作。支付完整流程只针对用户配置的测试支付环境和沙箱凭证。
- 用户触屏、前后台切换、焦点变化及自动化恢复/继续等纳入运行轨迹。运行允许继续并可根据断言正常判定；这些交互作为解释证据展示，不自动使运行失败。
- 本机调度、本地任务契约、凭证和运行证据由测试 App 本地管理。凭证允许明文保存在任务配置中，仅限测试沙箱；HTML/PDF/ZIP 导出前执行秘密剔除，导出结果不得包含原始凭证。
- 沙箱交易记录携带测试运行 ID。清理策略由任务配置指定并在报告中记录；清理失败不能静默抹除，需保留可追溯状态。
- 报告至少提供 HTML、ZIP 和 PDF。FAIL/错误步骤应关联截图；截图无法获取时显示缺失原因。ZIP 包含报告、允许导出的事件轨迹与截图及版本元数据，但过滤秘密。
- 测试 App 的上游同步流程需拉取 Mika 上游变更、应用测试工作区改动、构建并执行回归，然后发布到测试 App 专用更新通道。测试报告记录上游提交/版本标识和测试 App 版本；测试 App 更新不得覆盖或冒充官方 Mika 更新。
- 支持 Android 12 及以上；Android 12/13 焦点限制纳入设备兼容说明和测试覆盖范围。

## Testing Decisions

- 以外部可观察行为为测试标准：给定任务契约与目标 App 状态，验证运行 ID、用户可见状态、断言结论、轨迹、截图关联、导出内容和更新行为；避免只验证私有方法调用或内部实现细节。
- 在 `:app` 验证 `TestExecutionService` 经现有 `TaskService` 执行并写入 `RunStore` 的端到端接缝，覆盖成功、硬断言失败、软断言解释、执行异常、截图关联、用户交互事件、取消/恢复及不确定交易结果只读核查。
- 在 `:core` 验证任务契约解析、YAML/JSON 校验与版本兼容、硬/软断言聚合、不可被 LLM 覆盖的硬失败、报告投影和秘密剔除等纯逻辑行为。
- Android instrumentation 使用实际任务服务路径和可控目标 App/模型替身验证整条运行轨迹；支付沙箱测试使用隔离测试环境，不连接真实资金账户。
- 导出测试检查 HTML/PDF/ZIP 内的失败截图和运行元数据，并明确断言所有已配置凭证均未出现在导出产物中。
- 调度测试验证本机调度创建、触发、重复周期、重启后恢复和禁用/删除；对触发时设备离线、目标 App 不可用等情况验证报告状态与后续调度行为。
- 更新测试覆盖独立 application ID/签名/通道的包完整性与升级判定，确保测试 App 更新不会被官方 Mika 更新覆盖，且上游同步后的版本元数据可在报告中读取。
- 现有测试先例包括 `EvalRunTest` 和 `TaskServiceTest` 的真实执行路径，`RunStoreTest` 的运行数据持久化，以及 `ChecksTest`、`EvalReportTest` 对断言与报告逻辑的覆盖；`UpdateCheckerTest` 和 `ApkIntegrityTest` 是更新通道与 APK 校验的先例。

## Out of Scope

- 云端设备农场、远程设备控制、集中式远程调度和云端运行记录同步。
- iOS 支持或 Android 12 以下设备支持。
- 对目标 App 注入专用 SDK、修改目标 App，或要求目标 App 提供测试接口。
- 对真实支付资金、生产订单或未授权第三方系统执行自动化交易；完整交易仅限支付测试环境。
- 通过 LLM 语义解释推翻订单、支付等硬断言的失败。
- 保证 UI 动态变化时每次运行采取完全相同的动作；固定的是任务契约和模型策略版本，运行仍根据实时界面自主操作。
- 将原 Mika 应用替换为测试专用产品，或改变原 Mika 官方更新通道。
- 自动清除所有测试数据而不留运行关联记录；清理行为必须遵守配置策略并保留审计状态。

## Further Notes

- 产品目标是“基于 Mika 做一个独立测试 App，同时完整保留 Mika 功能并增加测试工作区”。测试 App 与原 Mika 可并存安装；用户选择测试 App 的独立更新通道，上游同步、构建和回归后发布。
- 用户接受脚本内明文沙箱凭证，因此本规格把导出剔除作为强制要求。执行记录和手机本地存储中仍会存在凭证的本地安全风险；实现应限制凭证的展示与导出路径，并明确该能力仅用于沙箱。
- 用户触屏后继续运行且允许正常 PASS 是已确认行为。轨迹必须区分自动化动作与人工交互，报告保留两者的时间顺序，使 PASS 仍可解释。
- 上游源码副本当前包含 `:app` Android 宿主和 `:core` Kotlin/JVM 模块，已有 Mika 任务运行、事件/截图存储、评测断言报告及更新完整性测试能力。测试工作区应优先复用这些能力，避免另建一套手机操作引擎。
- 规格发布到 issue tracker 尚未完成：当前工作区未提供 issue tracker 或 triage 标签词汇，且本机没有 `gh` 命令。按 `to-spec` 技能要求，需要先运行 `/setup-matt-pocock-skills` 配置 tracker 与 triage 词汇；之后才能将本文发布为 issue 并应用 `ready-for-agent` 标签。
